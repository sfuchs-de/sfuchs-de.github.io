Collection and provenance

Details

The reader is a static publication layer. A scheduled build collects metadata, resolves versions, ranks candidates against project profiles, generates bounded summaries, validates the issue, and writes HTML, JSON, RSS, Markdown, and BibTeX artifacts.

01

Collect

Official APIs, structured metadata tables, and verified feeds are preferred to publisher-page scraping.

02

Resolve

DOIs, repository identifiers, normalized titles, authors, and conservative fuzzy matching connect multiple versions of one work.

03

Select

Each candidate is scored against active projects, open questions, transferable methods, data needs, negative signals, and Paperpile novelty.

04

Publish

A validated weekly snapshot is rendered as a lightweight static site, with source health and machine-readable provenance beside it.

02

Issue safeguards

No canonical work may appear twice in one issue.

Every visible paper must have a project match and an explicit reason for inclusion.

Every summary records whether it used a title, abstract, or full text.

Source failures and partial failures remain visible rather than being silently treated as zero new papers.

Previously published issue snapshots remain unchanged; corrections are recorded as amendments.

03

Deployment

The generated reader contains only static HTML, CSS, JavaScript, JSON, XML, and BibTeX files. The included workflow serves them through GitHub Pages, while the same generated directory can also be copied to conventional Apache hosting or another static-file host.

That separation keeps the weekly collection process private and auditable while making the public reader extremely lightweight.
